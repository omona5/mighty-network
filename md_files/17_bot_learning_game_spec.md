# 마이티 게임 로직 및 딥러닝 봇 학습 명세

> 기준 구현: `server-node/src/RoomManager.js`, `server-node/src/game/RuleEngine.js`,
> `server-node/src/game/Scoring.js` (2026-10-05 확인).
>
> 이 문서는 **현재 서버가 실제로 판정하는 규칙**을 우선 기록한다. `권장 학습 환경`은
> 아직 서버 구현이 아닌, 봇 학습을 위해 추가해야 하는 인터페이스/설계다. 두 항목을 혼동하지 않는다.

## 1. 환경 개요

이 게임은 조커 1장을 포함한 53장 카드로 하는 5인 마이티다. 한 판은 입찰, 주공의
바닥패 교환, 프렌드 지정, 10개 트릭, 정산의 순서로 진행된다.

- 인원: 항상 5명. 대기실의 빈자리는 현재 단순 봇으로 채울 수 있다.
- 덱: 4무늬 × 13랭크 + 조커 = 53장.
- 배분: 각 플레이어 10장(총 50장), 바닥패 3장.
- 트릭: 5장이 한 트릭이며 총 10트릭.
- 팀: 주공 1명 + 프렌드 0 또는 1명 대 수비 3~4명.
- 점수 카드: `10`, `J`, `Q`, `K`, `A`가 각 1점, 전체 20점.
- 서버 권위: 카드 보유, 합법 행동, 승자 및 점수는 서버가 계산한다. 클라이언트는 권위 상태가 아니다.

학습 관점에서 게임은 다음 두 성질을 동시에 가진다.

1. 각 봇은 자기 손패만 볼 수 있는 **부분관측(POMDP)** 환경이다.
2. 카드 프렌드가 공개되기 전에는 팀원이 숨겨진 **동적 협력/대전** 환경이다.

따라서 모든 플레이어의 손패나 바닥패를 정책 입력에 넣으면 실제 게임에서는 사용할 수 없는
정보 누설(cheating)이 된다. 다만 비평가(centralized critic), 시뮬레이터 검증, 오프라인
분석용 전역 상태에는 사용할 수 있다.

## 2. 카드 표현 및 고정 인덱스

### 2.1 카드 ID

| suit | ID 접두어 | rank |
| --- | --- | --- |
| `SPADE` | `S_` | `2`~`10`, `J`, `Q`, `K`, `A` |
| `HEART` | `H_` | 동일 |
| `DIAMOND` | `D_` | 동일 |
| `CLUB` | `C_` | 동일 |
| `JOKER` | `JOKER` | `JOKER` |

예: 스페이드 A는 `S_A`, 하트 10은 `H_10`이다. 점수값 `point`는 점수 카드면 1,
그 외와 조커는 0이다.

학습 데이터에는 카드 53장을 변하지 않는 순서로 인덱싱해야 한다. 권장 순서는 서버 덱 생성
순서와 같은 `SPADE[2..A]`, `HEART[2..A]`, `DIAMOND[2..A]`, `CLUB[2..A]`, `JOKER`다.
손패와 행동 마스크에 이 인덱스를 공통으로 쓴다.

### 2.2 랭크 강도

일반 카드의 랭크 강도는 `2 < 3 < ... < 10 < J < Q < K < A`이다. 단, 트릭 비교는
랭크만으로 하지 않으며 아래 특수 우선순위를 먼저 적용한다.

## 3. 한 판 상태 전이

```text
waiting
  → bidding
  → exchanging_kitty
  → choosing_friend
  → playing (10개 트릭)
  → finished
  → waiting
```

| 상태 | 행동 주체 | 합법 행동 | 상태 전이 |
| --- | --- | --- | --- |
| `waiting` | 참가자/방장 | 준비, 시작, 봇 추가/제거 등 | 5명 준비 후 `bidding` |
| `bidding` | 현재 입찰자 | 공약, 패스, 조건 충족 시 딜미스 | 낙찰 시 `exchanging_kitty` |
| `exchanging_kitty` | 주공 | 13장 중 정확히 3장 버리기 | `choosing_friend` |
| `choosing_friend` | 주공 | 카드/플레이어/노프렌드 선택 | `playing` |
| `playing` | 현재 턴 플레이어 | 합법 카드 1장, 필요 시 리드 옵션 | 10번째 트릭 후 `finished` |
| `finished` | 전체 | 결과 확인, 대기실 복귀 | `waiting` |

입찰에서 모두 패스하면 최소 공약을 `13 → 12 → 11`로 낮춰 다시 입찰한다. 11에서도
모두 패스하면 재배분 후 13부터 다시 시작한다. 딜미스도 즉시 재배분/재입찰이다.

## 4. 입찰 단계

### 4.1 행동 공간

입찰 행동은 다음 둘 중 하나다.

```json
{ "type": "bid", "targetScore": 13, "trumpSuit": "HEART", "noTrump": false }
{ "type": "pass_bid" }
```

- `targetScore`: 현재 라운드 최저 공약 이상, 20 이하의 정수.
- 최고 공약이 있으면 그보다 **최소 1 높아야** 한다.
- `noTrump=false`라면 `SPADE|HEART|DIAMOND|CLUB` 중 하나를 선택한다.
- `noTrump=true`라면 기루다는 `null`이다.
- 패스한 플레이어는 같은 입찰 라운드에서 다시 공약할 수 없다.
- 최고 공약자만 남거나 전원이 패스하면 입찰이 끝난다.

낙찰자는 주공(declarer)이 된다. 낙찰 공약은 이후 목표점 `targetScore`, 선택한 기루다는
`trumpSuit`가 된다. 현재 기본 봇은 노기루를 선택하지 않는다. 이는 규칙 제한이 아니라
기존 휴리스틱의 한계다.

### 4.2 딜미스

입찰 또는 패스를 한 번도 하지 않은 플레이어만 딜미스를 선언할 수 있다.

```text
딜미스 점수 = (A/K/Q/J 각 +1) + (10 각 +0.5) + (조커 각 -1) + (마이티 S_A는 0)
선언 가능 조건: 딜미스 점수 ≤ 0.5
```

이 단계에서는 기루다가 정해지기 전이므로 딜미스의 마이티는 항상 `S_A`로 계산한다.
성공 시 승패/점수 없이 재배분한다. 학습 환경에서는 이 행동을 입찰 정책의 별도 이산
행동으로 두고, 조건 불충족 시 마스킹해야 한다.

## 5. 바닥패와 프렌드

### 5.1 바닥패 교환

입찰 종료 후 주공만 비공개 바닥패 3장을 받아 손패가 13장이 된다. 주공은 자신의 13장 중
서로 다른 3장을 골라 버려 정확히 10장을 남긴다.

- 버린 3장은 게임 중 수비팀에게 공개되지 않는다.
- 버린 카드의 점수는 종료 시 주공팀 점수로 합산된다.
- 주공의 버리기 정책은 독립된 다중 선택 행동이다. 순차로 3장을 뽑게 만들거나, 53비트
  multi-binary 출력 중 정확히 3개를 선택하도록 설계할 수 있다.
- 순차 선택 방식은 매 선택 후 이미 고른 카드를 마스킹하고 3번째 선택 후 다음 단계로
  전이하므로 구현과 PPO류 학습이 단순하다.

### 5.2 프렌드 선택

주공은 아래 세 방식 중 하나를 택한다.

| 방식 | 입력 | 공개 시점 | 팀 구성 |
| --- | --- | --- | --- |
| 카드 프렌드 | `friendCardId` | 그 카드가 플레이될 때 | 해당 카드 소유자 |
| 플레이어 프렌드 | `friendClientId` | 즉시 | 지정 플레이어 |
| 노프렌드 | `friendCardId: "NONE"` | 즉시 | 주공 단독 |

카드 프렌드는 현재 주공이 보유한 카드도 지정 가능하다. 그 경우 카드가 나올 때까지 숨겨지고,
종료 정산에서는 주공 자신을 프렌드로 중복 계산하지 않아 단독 팀으로 취급한다. 지정 카드가
끝까지 나오지 않는 경우도 주공 단독 팀으로 정산된다.

카드 프렌드 행동의 후보는 모든 53장이다. 다만 실제 UI/서버에는 **자기 손패가 아닌 카드만**
선택하게 하는 제한이 없으므로, 학습 환경도 현재 동작을 재현하려면 모든 카드를 허용해야 한다.
전략 품질을 위해서는 자기 카드 선택에 불이익을 주거나 향후 룰에서 금지하는 방안을 별도로
결정해야 한다.

## 6. 트릭 규칙

### 6.1 마이티와 조커콜

입찰에서 확정한 설정은 다음과 같다.

| 조건 | 마이티 | 조커콜 카드 |
| --- | --- | --- |
| 기루다 = `SPADE` | `D_A` | `C_3` |
| 기루다 = `CLUB` | `S_A` | `S_3` |
| 기루다 = `HEART` 또는 `DIAMOND` | `S_A` | `C_3` |
| 노기루 | `S_A` | `C_3` |

마이티는 항상 최강이다. 조커는 첫 번째와 마지막(10번째) 트릭에서는 특수 최강 효과가 없다.
중간 트릭에서만 마이티 다음의 강한 카드다. 조커콜이 활성화된 트릭에서는 조커도 특수 효과가
없다.

### 6.2 리드와 따라내기

각 트릭의 첫 카드가 리드 카드다.

- 일반 카드 리드: 해당 카드의 무늬가 리드 무늬다.
- 조커 리드: `declaredSuit`로 4개 일반 무늬 중 하나를 반드시 선언하며, 선언 무늬가 리드
  무늬다.
- 손에 리드 무늬의 일반 카드가 있으면 그 무늬를 반드시 내야 한다.
- 단, **마이티와 조커는 따라내기 예외**라서 리드 무늬가 있어도 낼 수 있다.
- 리드 무늬가 없으면 어떤 카드든 낼 수 있다.
- 새 트릭은 이전 트릭의 승자가 리드한다.

### 6.3 조커콜

조커콜 카드를 리드할 때만 `activateJokerCall`을 선택할 수 있다.

- 조커가 아직 한 번도 나오지 않았을 때에만 활성화할 수 있다.
- 활성화된 조커콜에 대해, 조커 보유자는 다른 카드(마이티 포함)를 낼 수 없고 조커를 반드시
  내야 한다.
- 조커 보유자가 아니면 일반 따라내기 규칙이 적용된다.
- 조커콜이 활성화된 트릭에서는 조커가 최강이 아니며 일반 카드처럼 취급되어 승자 비교에서
  제외된다.

서버 오류 메시지에는 조커콜에서 “마이티로 막을 수 있음”이라는 문구가 있으나 실제
`canPlayCard` 구현은 조커 보유 시 마이티도 금지한다. 학습 명세는 **실제 함수의 동작**을
따른다.

### 6.4 트릭 승자 결정

5장이 모두 나오면 아래 우선순위로 승자를 정한다.

1. 마이티가 있으면 마이티를 낸 플레이어.
2. 1·10트릭이 아니고 조커콜 활성 리드도 아니라면, 조커를 낸 플레이어.
3. 기루다가 있으면 가장 높은 랭크의 기루다 카드.
4. 가장 높은 랭크의 리드 무늬 카드.
5. 위에 해당하는 일반 카드가 없으면 리더.

조커 리드의 선언 무늬가 누락된 비정상 상태에서는 서버가 첫 일반 카드의 무늬를 보조적으로
사용하지만, 정상 정책은 항상 유효한 `declaredSuit`를 보내므로 이 경우를 생성하면 안 된다.

## 7. 점수와 종료 보상

### 7.1 팀 점수 및 승패

각 트릭의 5장은 해당 트릭 승자의 획득 카드가 된다. 종료 시:

```text
주공팀 점수 = 주공의 획득 점수 + 공개된 프렌드의 획득 점수 + 버린 바닥패 점수
수비팀 점수 = 나머지 플레이어의 획득 점수
주공팀 승리 ⇔ 주공팀 점수 ≥ targetScore
```

카드 프렌드가 공개되지 않았으면 그 플레이어의 획득 점수는 수비팀으로 계산된다. 전체 점수는
항상 20점이다.

### 7.2 정산 배수

| 조건 | 배수 |
| --- | --- |
| 런: 주공팀 점수 20 | ×2 |
| 백런: 주공팀 점수 10 이하 | ×2 |
| 주공팀 승리 + 노기루 | ×2 |
| 주공팀 승리 + 노프렌드 | ×2 |

배수는 중첩 곱셈이다. 기본 판돈은 주공팀 승리 시 `max(1, 주공팀점수 - 10)`, 패배 시
`max(1, 목표점수 - 주공팀점수)`이며, 최종 판돈은 기본 판돈×배수다.

최종 개인 델타는 영합이다.

- 프렌드가 있으면: 주공 `±2U`, 프렌드 `±U`, 수비 3명 각각 `∓U`.
- 프렌드가 없으면: 주공 `±(수비 인원×U)`, 수비 각각 `∓U`.
- 부호는 주공팀 승리면 주공팀 양수, 패배면 반대다.

## 8. 학습용 환경 API 권장안

서버의 방/소켓 API와 분리된 순수 환경을 만든다. 난수 시드와 전체 상태를 주입할 수 있어야
재현 가능한 self-play, 리플레이, 단위 테스트가 가능하다.

```python
env = MightyEnv(num_agents=5, seed=1234, rules="current-server")
observations, infos = env.reset(seed=1234)
observations, rewards, terminated, truncated, infos = env.step(actions)
```

- `actions`: 현재 의사결정자가 하나일 때에도 5명 dictionary 형태를 유지하거나, turn-based
  wrapper를 제공한다.
- `observations[agent]`: 해당 agent가 합법적으로 아는 정보만 포함한다.
- `infos[agent]["action_mask"]`: 현재 행동 공간에서 합법인 행동만 1이다.
- `terminated`: 정산이 끝난 상태에서만 `true`.
- `truncated`: 시간 제한/디버그 중단 등의 외부 종료에만 사용한다.
- 서버와 동일한 `RuleEngine`을 공유하거나, 모든 시드·행동열에 대해 결과가 일치하는
  독립 구현을 테스트한다.

## 9. 관측 설계

### 9.1 공개 관측

모든 정책에 다음 정보를 준다.

- 자신의 상대 좌석 인덱스: 자신을 0으로 회전한 5인 좌석 표현.
- 단계 one-hot: 입찰/바닥패/프렌드/플레이/종료.
- 입찰: 현재 최저 공약, 최고 공약, 최고 공약의 무늬/노기루, 패스자 5비트, 현재 입찰자.
- 확정 계약: 주공 좌석, 목표점, 기루다 또는 노기루, 마이티 ID, 조커콜 ID.
- 프렌드: 방식, 카드 프렌드 ID(지정 사실은 공개), 공개 여부, 공개된 프렌드 좌석.
- 트릭: 트릭 번호 1~10, 현재 턴, 리드 좌석, 테이블 5슬롯의 `(좌석, 카드, 조커 선언무늬,
  조커콜 활성)`.
- 이력: 완료 트릭의 카드/승자, 각 좌석의 남은 손패 장수, 각 좌석의 획득 트릭 수.
- 공개된 특수정보: 마이티 보유자 공개 여부/좌석, 조커가 이미 나왔는지.
- 누적 점수와 이전 판 결과(세션 게임을 학습한다면).

### 9.2 개인 비공개 관측

- 자기 손패: 53차원 multi-hot.
- 바닥패 단계의 주공에게만: 13장 손패(바닥패 포함).
- 버린 뒤의 바닥패: 주공에게만 별도 53차원 multi-hot으로 유지 가능. 현재 서버의 진행 중
  점수 공개 규칙도 주공에게만 바닥패 점수를 준다.
- 카드 프렌드 소유 여부는 자기 손패에서 스스로 추론할 수 있지만, 다른 플레이어의 소유자는
  공개 전 입력으로 주면 안 된다.

전략망은 고정 길이 벡터나 카드/좌석 토큰 Transformer로 구현할 수 있다. 장기 기억이 필요한
게임이므로 완료된 트릭 이력을 잘라내는 경우 LSTM/GRU 또는 Transformer memory를 사용한다.

### 9.3 중앙집중 critic 전용 전역 상태

CTDE(centralized training, decentralized execution)에서만 다음을 critic에 제공한다.

- 5명 모두의 손패, 실제 바닥패, 실제 프렌드 카드 소유자.
- 모든 플레이어의 역할과 팀.
- 덱 순서/난수 시드(디버그에는 유용하지만 정책 입력에는 불필요).

Actor에는 절대로 포함하지 않는다.

## 10. 행동 인코딩 및 마스킹

학습 안정성을 위해 단계별 action head를 분리한다. 사용하지 않는 head는 마스크한다.

| 단계 | 권장 head | 합법 마스크 |
| --- | --- | --- |
| 입찰 | `PASS`, `DEAL_MISS`, `(공약 11~20 × 기루다 4 + 노기루)` | 차례, 최저/최고 공약, 딜미스 조건 |
| 바닥패 | 카드 53개를 3회 순차 선택 | 주공, 자기 13장, 이미 버린 카드 제외 |
| 프렌드 | 카드 53개 + 플레이어 상대 4명 + NONE | 주공, 카드/플레이어/NONE 형식 |
| 카드 내기 | 카드 53개 | 현재 턴, 자기 손패, `canPlayCard` |
| 조커 리드 | 선언 무늬 4개 | 리드 카드가 조커일 때 |
| 조커콜 리드 | 비활성/활성 2개 | 리드 카드가 조커콜이고 조커 미사용일 때 |

카드 내기 마스크는 모델이 재구현하지 말고 환경의 규칙 함수가 계산한다. 마스크 없는 정책은
불법 행동에 의한 샘플 낭비와 잘못된 가치 추정을 크게 만든다. 행동 마스크의 불변식은 다음이다.

```text
mask[card] = 1  ⇔  card ∈ 자기 손패 AND RuleEngine.canPlayCard(...) = true
```

테이블이 비어 있으면 모든 자기 손패 카드가 가능하지만, 조커 리드라면 선언 무늬 head도
반드시 유효한 한 값을 가져야 한다.

## 11. 보상 설계

### 11.1 가장 안전한 기본 보상

정산 델타를 그대로 terminal reward로 쓴다. 각 에이전트 `i`에 대해:

```text
R_i(final) = result.deltas[clientId_i] / reward_scale
```

`reward_scale`은 관측 가능한 최대 절대 델타(현재 룰에서는 큰 배수로 320까지 가능)에 맞춰
예를 들어 80 또는 320으로 정해 값을 대체로 `[-1, 1]` 범위로 만든다. 영합 구조와 실제
목적(정산 승리)을 정확히 보존한다.

주공과 공개/비공개 프렌드는 같은 팀 보상을 공유해야 한다. 카드 프렌드가 공개되기 전에는
정책이 자신의 팀을 모르는 것이 정상이며, 학습 종료 후 실제 역할에 따라 terminal reward를
귀속한다.

### 11.2 선택적 shaping

희소 보상이 너무 느리면 다음처럼 **잠재함수 기반 shaping**을 더한다.

```text
r'_t = r_t + γ Φ(s_{t+1}) - Φ(s_t)
```

`Φ`는 중앙집중 훈련에서만 정확하게 계산할 수 있는 주공팀의 기대 최종 정산가치(예: rollout
value)로 둔다. 이 방식은 terminal 목적의 최적 정책을 보존한다. 단순히 “점수 카드 1장을
먹으면 +1”을 주면 목표 공약, 팀 역할, 버린 바닥패, 백런 전략을 왜곡할 수 있으므로 기본
보상으로 사용하지 않는다.

학습 초반 커리큘럼에서는 별도 보조 목적을 쓸 수 있다.

- 불법 행동: 마스킹으로 원천 차단. 외부 패널티에 의존하지 않는다.
- 트릭 승자 정확성/합법 수 예측: supervised auxiliary head.
- 입찰 후 계약 성공 여부: 주공/수비 팀 단위 보조 reward.
- 점수 카드 획득: 매우 작은 보조치만 쓰고 최종 정산 보상과 분리해 ablation한다.

## 12. 학습 절차 권장안

1. **규칙 검증**: 고정 시드로 deal → action sequence → winner/점수/마스크를 서버 테스트와
   대조한다.
2. **단일 트릭 커리큘럼**: 무작위 손패/기루다에서 합법 카드 마스크, 승자 판정을 학습/검증한다.
3. **카드 플레이 self-play**: 계약과 팀을 고정한 10트릭 환경으로 시작한다.
4. **프렌드 포함 self-play**: 카드 프렌드와 공개 시점을 추가한다.
5. **바닥패/입찰 추가**: 전체 한 판 정책으로 확장한다.
6. **리그 self-play**: 최신 정책만 상대로 두지 말고 과거 체크포인트, 휴리스틱, 탐색 강화
   정책을 섞어 과적합/망각을 줄인다.

MAPPO + centralized critic은 5인 협력/대전 및 부분관측에 적합한 첫 선택이다. 카드 게임의
탐색을 강화하려면 행동 마스크를 적용한 PPO 계열에 MCTS/rollout teacher를 더하거나, 대량
자체대국으로 AlphaZero류 정책·가치 학습을 검토할 수 있다.

현재 내장 봇은 강한 기준선이 아니다. 입찰은 단순 손패 점수 휴리스틱, 바닥패는 약한 카드
3장 폐기, 플레이는 합법 카드 중 대체로 무작위 선택이다. 이를 dataset teacher로 쓰기보다
초기 smoke test 또는 약한 상대 풀로만 사용한다.

## 13. 에피소드 로그 형식

재현/오프라인 학습용으로 다음 메타데이터를 모든 결정 시점에 저장한다.

```json
{
  "episode_id": "uuid",
  "seed": 1234,
  "step": 27,
  "acting_seat": 3,
  "phase": "playing",
  "observation": { "...": "actor에게 공개 가능한 상태만" },
  "action_mask": [0, 1, 0],
  "action": { "cardId": "H_K" },
  "reward": 0,
  "terminated": false,
  "public_event": { "type": "card_played", "cardId": "H_K" },
  "debug_global_state": { "...": "훈련/감사용, actor 입력 금지" }
}
```

`debug_global_state`는 별도 권한/파일로 분리한다. actor 관측과 전역 상태를 같은 JSON에
넣고 전처리하면 정보 누설이 발생하기 쉽다.

## 14. 구현 불변식 및 테스트 체크리스트

- 매 deal: 손패 합계 50장, 바닥패 3장, 중복 카드 0장.
- 바닥패 교환 후: 모든 플레이어 손패가 10장, 버린 패 3장.
- 매 트릭: 정확히 5장의 서로 다른 카드, 승자가 다음 리드.
- 종료: 모든 손패 0장, 트릭 10개, 모든 획득/바닥패 카드 합계 53장.
- 점수 카드 총합: 항상 20점.
- 팀 정산 델타 총합: 항상 0.
- `canPlayCard`가 true인 카드가 현재 카드 행동 마스크에서 정확히 1.
- 조커 리드에는 유효한 선언 무늬가 반드시 존재.
- 조커콜 활성 상태에서 조커 보유자의 합법 카드 집합은 조커 1장이다.
- 첫/마지막 트릭에서 조커는 마이티보다 약하고 일반 조커 최강 효과가 없다.
- 카드 프렌드 공개 전에는 actor 관측에 실제 프렌드 좌석이 없다.

## 15. 현재 구현에 맞춘 주의점

- 지역 룰 변형(초구 기루다 금지, 바닥패 뒤 기루다 변경, 다른 백런 기준 등)은 현재 적용하지
  않는다. 학습 데이터와 실제 서버의 룰 버전은 반드시 함께 기록한다.
- 봇/연결 끊긴 사람의 자동 행동과 30초 인간 타이머는 네트워크 UI 편의 기능이다. 오프라인
  학습 환경에서는 제거하고 환경 step을 즉시 진행한다.
- 진행 중 수비팀은 바닥패 점수를 알 수 없고, 주공만 알 수 있다. 관측 설계에서 이를 지킨다.
- 이 문서는 현재 서버의 정의이며, 규칙을 바꾸면 `RuleEngine`, `Scoring`, 이 문서, 환경
  회귀 테스트를 같은 변경으로 갱신해야 한다.
