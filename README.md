# Mighty Network

Unity WebGL 클라이언트와 Node.js WebSocket 서버로 만든 5인용 마이티 카드 게임이다.
게임 규칙과 상태는 서버가 판정하고 Unity 클라이언트는 입력과 화면 표시를 담당한다.

## 구조

- `mighty-network-unity/`: Unity 6 클라이언트
- `server-node/`: HTTP/WebSocket 게임 서버
- `scripts/`: 로컬 개발 서버 시작·종료 도구
- `md_files/`: 설계 및 단계별 구현 문서

## 로컬 개발

```powershell
.\scripts\Start-LocalServer.ps1
```

서버 상태는 `http://localhost:3000/health`, 브라우저 테스트 페이지는
`http://localhost:3000`에서 확인한다. Unity 프로젝트는
`mighty-network-unity/`를 Unity Hub에서 연다.

```powershell
.\scripts\Stop-LocalServer.ps1
```

서버 테스트는 `server-node/`에서 `npm test`로 실행한다.

## 봇 및 입찰 정책

- 딜미스 조건을 만족한 사람은 배분 직후 별도 버튼으로 차례와 무관하게 선언할 수 있다.
  해당 입찰 라운드에서 이미 공약 또는 패스한 뒤에는 선언할 수 없다.
- 봇은 접속 중인 사람들의 배분 애니메이션 완료 신호를 모두 받은 뒤 3초를 기다려
  딜미스를 자동 선언한다. 입찰 차례와 무관하며 여러 봇이 해당해도 한 번만 재배분한다.
  완료 신호가 오지 않는 클라이언트는 기존 30초 제한 후 배분 완료로 취급한다.
- 봇 입찰 상한은 손평가에서 1.5 차감 후 내림하며, 경쟁 입찰은 다음 공약보다 1점의
  여유가 있어야 참여한다. 실제 공약은 허용되는 최소 점수다.
- 8종 모두 다른 후보가 있으면 마이티 선공을 피하고, 팔로우는 테이블 점수와 마이티를
  합쳐 2점 이상일 때만 마이티를 후보에 둔다. 이는 사용 허용 조건이며 사용 강제는 아니다.
  기존 1·10트릭 조커 회피와 9트릭 조커 우선 규칙이 먼저 적용된다.
- ConservativeBot 비용 기준은 문서의 카드명 설명대로 기루 J 이상, 비기루 Q 이상이다.
- 첫 판은 첫 좌석부터 입찰한다. 다음 판은 이전 완료 판의 주공이 좌석 이동과 무관하게
  시작한다. 유찰·재배분에서도 같은 시작자를 사용하며, 이전 주공이 나갔으면 첫 좌석으로 돌아간다.

## 게임 기록 (학습·분석용)

실제 서버는 일반 게임을 기본적으로 `server-node/data/games/YYYY-MM-DD/<gameId>.jsonl`에
저장한다. 날짜와 시각은 UTC이며 배분마다 새 UUID를 발급한다. 튜토리얼은 제외한다.
`GAME_LOG_DIR` 환경 변수로 저장 경로를 바꿀 수 있다. 운영 환경에서는 영속 디스크를
지정하고 백업해야 한다. 공개 정적 파일 경로(`public/`)에는 저장하지 않는다.
기본 기록 폴더는 Git에서 제외되며 자동 삭제되지 않는다.

각 줄은 독립 JSON 이벤트다. `schemaVersion`, 서버 실행별 `runId`, `gameId`, `roomId`,
연속 번호 `seq`, 시각 `at`, 이벤트 종류 `type`, 상세 `data`, 행동 후 전체 상태 `state`를 담는다.
카드는 기존 `{id, suit, rank, point}` 형식이다. 좌석은 0부터 시작한다.

| 이벤트 | 저장 내용 |
|---|---|
| `deal` | 각 좌석 초기 10장, 최초 바닥패 3장, 봇 정책 버전 |
| `bidding_start`, `bid`, `bid_pass`, `all_pass` | 입찰 라운드 최소점, 모든 공약·패스, 기루다·노기루, 유찰 |
| `contract` | 확정 주공, 공약 점수, 기루다, 규칙 설정 |
| `kitty_pickup`, `kitty_discard` | 주공이 가져간 3장, 버린 3장, 교환 후 손패 |
| `friend_choice` | 카드·플레이어·노프렌드 지정 및 실제 프렌드 신원 |
| `deal_miss` | 선언자와 딜미스 점수 (다음 배분은 별도 게임 ID) |
| `play_start`, `play` | 플레이어·좌석·카드·트릭 번호·트릭 내 순서, 조커 선언 무늬, 조커콜 활성 여부 |
| `trick_end` | 순서대로 낸 5장과 플레이어, 승자, 점수패 합계, 개인별 트릭 승리 여부 |
| `game_end` | 종료 사유, 정상 종료 시 팀 승패·점수·프렌드·개인 정산·누적 점수 |

`state.players`에는 당시 모든 손패·획득패·닉네임·봇 여부·연결 상태·봇 정책이 들어간다.
`play.data.controller`는 `human`(사용자 제출), `bot`(봇), `auto`(시간 초과 또는 연결 해제된
사람의 자동 플레이)를 구분한다. `state`에는 미공개 프렌드와 버린패도 포함되므로
클라이언트에 전송하지 않는다. 방 비밀번호, 재접속 토큰, 소켓 정보는 기록하지 않는다.
플레이 직전 관측은 직전 이벤트 상태에서 구성할 수 있다. 학습 actor 입력을 만들 때는
상대 손패·미공개 프렌드·타인의 버린패를 반드시 제외한다.

종료 사유는 `finished`, `redealt`, `no_humans`, `returned_to_lobby`, `server_shutdown`이다.
`finished` 이외의 판을 정상 완료 학습 표본과 분리한다. 강제 종료 시 `game_end`가 없을 수
있으며 이를 미완료 판으로 취급한다. 파일 끝이 잘린 JSON이면 마지막 불완전 줄은 무시한다.
`seq`가 누락된 기록도 학습에서 제외한다.

행동이 확정될 때마다 동기 append로 기록한다. 저장 실패 시 게임은 계속되며 서버 오류
로그와 `/health`의 `gameRecording.writeErrors`, `lastErrorAt`에서 확인할 수 있다.
전원 장애까지 보장하는 fsync/복제 저장은 제공하지 않는다. 동시 방이 많아지면 디스크 쓰기
지연을 측정하고 전용 기록 큐/DB로 전환한다. 배포 시 `GAME_CODE_VERSION`에 커밋 ID 등을
지정하면 `deal.data.serverRevision`으로 정책·규칙 버전을 추적할 수 있다.
